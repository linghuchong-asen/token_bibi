# token比比 — 产品规格大纲（Draft）

- **产品名**：token比比
- **状态**：Draft，等待确认
- **日期**：2026-10-21
- **目标**：做一个面向开发者、独立产品人、AI 重度用户的「AI 模型 API 成本决策工具」，把 **按量、订阅、积分/点数/额度、卡密/兑换码** 四类获取方式放在同一套可比较的口径里。
- **一句话定位**：
  **「不要只看单价，先看真实到手成本。」**

## 1. 背景

### 1.1 现状
- **Oken** 已经把模型级 token 单价、可用性、模型一致性、稳定性做得比较完整。
- **Oken 当前核心口径仍然偏“按量计费”**，对订阅、积分/点数、卡密/兑换码等购买路径覆盖不足。
- **PriceAI** 把购买路径拆成：
  1. 官方订阅
  2. 卡网订阅
  3. 官方 API
  4. 中转 API
  它的价值在于先把用户按“购买路径”分流，再进入对应工具页。
- **New API 生态** 已经在官方文档中明确支持：
  - 余额 / 内部额度
  - 在线充值
  - 兑换码
  - 订阅计划
  - 分组与倍率
  - 标准价格 / 充值价格
- **OpenRouter** 采用“credits + pay-as-you-go”的模型，用户购买 credits 后按 token 扣费。

### 1.2 问题
用户真正的决策问题不是“哪家 token 单价最低”，而是：

> 在我的用量、并发、预算、稳定性要求和合规边界下，我到底应该：
> - 按量买？
> - 订阅包？
> - 充值积分？
> - 买兑换码 / 卡密？
> - 还是混合使用？

目前大部分工具仍然把这个问题拆散在不同平台、不同页面、不同口径里。

## 2. 产品目标

1. **统一口径**：把“标价、充值汇率、倍率、订阅额度、卡密/兑换码”统一折算成可比较的有效成本。
2. **减少误判**：用户能一眼看出“表面便宜”和“实际便宜”的差别。
3. **路径选择**：不只比较模型价格，还比较购买路径、支付方式、退款边界、稳定性和风险。
4. **零预算增长**：产品功能、页面结构和文案设计都必须服务于自然流量、社区传播和开发者自传播。
5. **可持续商业化**：用清晰的赞助、广告、AFF 或数据服务变现，但不得影响排序和风险提示。

## 3. 核心范围

### 3.1 一级功能
1. **模型比价**
   - 输入价、输出价、缓存价
   - 按百万 tokens / 千 tokens 切换
   - 人民币 / 美元显示
   - 模型能力标签
2. **平台比价**
   - 官方 API
   - 聚合平台
   - 中转 API
   - New API / 自部署网关
3. **计费路径**
   - 按量计费
   - 订阅套餐
   - 积分 / 点数 / 额度
   - 卡密 / 兑换码
4. **有效成本计算**
   - 充值倍率
   - 分组倍率
   - 平台折扣
   - 订阅额度折算
   - 最低充值
   - 余额有效期
5. **风险与可信度**
   - 数据来源
   - 最近核验时间
   - 公开价格页 / 监测页链接
   - 上游类型
   - 退款与售后
   - 支付方式
6. **场景化推荐**
   - 低成本验证
   - 稳定生产
   - 高并发
   - 长上下文
   - 企业发票与合同
   - 个人小额试错
7. **营销增长系统**
   - 可分享比价卡片
   - 可嵌入小组件
   - 长尾 SEO 页面
   - 开放数据与 GitHub 传播
   - 社区发布模板

## 4. 非目标（MVP 不做）

1. **不做交易平台**：不替用户下单、充值、开账号。
2. **不做账号买卖**：不收录不可公开核验的账号渠道。
3. **不做担保**：收录不等于推荐，所有平台都需明确风险边界。
4. **不做实时全量抓取**：优先人工核验 + 公开接口 + 定期快照。
5. **不做复杂 Agent 比价**：先解决 token 成本和购买路径，能力评测只做基础标签。
6. **不做灰色内容**：不采集绕过风控、违反上游条款或合规风险不明的渠道。

## 5. 关键假设

1. 目标用户主要是中文开发者、独立产品人、AI 重度用户、小型技术团队。
2. 用户更在意“决策可靠”和“少踩坑”，其次才是页面华丽。
3. 初期数据量不需要大而全，但**口径必须准确、来源必须可追溯**。
4. 订阅、积分/点数、卡密/兑换码在真实生态中确实存在，需要纳入，但应根据属性拆分：
   - **订阅**：一级计费维度
   - **积分/点数/额度**：一级计费维度
   - **卡密/兑换码**：购买路径和风险维度，不应简单等同于价格维度
5. 零预算营销优先级高于界面装饰。

## 6. 开放问题

1. 是否先聚焦 **New API / API 中转平台**，还是同时覆盖官方 API 与聚合平台？
2. 订阅套餐的“有效成本”是否要默认按 30 天折算？
3. 卡密/兑换码是否只作为支付方式记录，还是需要单独比价页？
4. 是否需要用户提交平台资料，还是先由人工审核种子数据？
5. 是否把 Oken 的“模型一致性检测”作为后续功能，而不是 MVP？
