# token比比 — 产品需求文档（PRD）

- **产品名**：token比比
- **版本**：v0.1
- **状态**：Draft，等待确认
- **日期**：2026-10-21
- **负责人**：个人产品 / 独立开发者

## 1. 背景

### 1.1 市场问题
用户在选择 AI 模型服务时，面对的不是单一价格，而是四种不同口径：

1. **按量计费**：按输入、输出、缓存 token 收费。
2. **订阅计费**：按月或按年购买额度、分组、模型范围。
3. **积分 / 点数 / credits / 额度**：先充值内部额度，再按模型和倍率扣减。
4. **卡密 / 兑换码 / 网卡**：通过兑换码、卡密或外部渠道获得服务。

现有工具往往只比较其中一种，或者把购买方式、价格、风险、稳定性混在一个表格里，导致用户难以判断真实到手成本。

### 1.2 竞品观察
- **Oken**：强在模型级按量价格与稳定性，但订阅、积分、卡密等购买路径覆盖不足。
- **PriceAI**：强在按购买路径分流，明确声明商业合作不影响排序。
- **New API 生态**：文档明确支持余额、充值、兑换码、订阅计划。
- **OpenRouter**：采用 credits + pay-as-you-go 模式。

### 1.3 产品机会
做一个以 **“真实到手成本”** 为核心的决策工具：

> 表面单价便宜，不等于实际便宜。
> 订阅便宜，不等于在你的用量下便宜。
> 充值有折扣，不等于没有汇率、有效期、分组倍率和退款限制。

## 2. 产品定位

### 2.1 一句话定位
**token比比是一个面向开发者和 AI 重度用户的 AI 模型 API 成本决策工具，用来比较按量、订阅、积分和卡密四类购买方式的真实成本。**

### 2.2 核心价值
1. **统一口径**：把不同计费方式折算成可比较的有效成本。
2. **降低踩坑**：把充值汇率、余额有效期、订阅限制、退款边界结构化展示。
3. **购买路径选择**：告诉用户该走按量、订阅、积分还是卡密。
4. **零预算增长**：产品本身要能自然传播。

## 3. 目标用户

### 3.1 主要用户
1. **独立开发者**
   - 关注成本、可测试性和小额试错。
2. **AI 重度用户**
   - 关注订阅额度、模型范围、并发和稳定性。
3. **小型技术团队**
   - 关注发票、合同、退款、权限和企业协作。
4. **产品与技术决策者**
   - 关注总拥有成本、供应商风险和迁移成本。

### 3.2 次要用户
1. API 中转站运营者
2. AI 工具开发者
3. 技术内容创作者
4. 社区活跃用户

## 4. 用户故事

### US-1：个人开发者小额试错
> 我刚想接入一个新模型，预算只有几十元。
> 我想知道哪家支持最低充值、小额测试，且不坑费。

### US-2：AI 重度用户选择订阅
> 我每个月固定用某几个模型。
> 我想知道订阅是否比按量便宜，额度会不会重置，超额后怎么算。

### US-3：开发者比较充值汇率
> 我看到两个平台 token 单价差不多。
> 我想知道它们的充值汇率、折扣、余额有效期和最低充值差异。

### US-4：技术负责人评估平台
> 我要给团队选一个稳定服务。
> 我想知道上游类型、发票、退款、并发和客服情况。

### US-5：社区用户分享结论
> 我算出了一个很反直觉的比价结论。
> 我想生成一张卡片或链接，直接发到群里。

## 5. 功能需求

## FR-1 模型比价首页

**描述**
- 展示模型级输入价、输出价、缓存价。
- 支持按百万 tokens / 千 tokens 切换。
- 支持人民币 / 美元显示。
- 展示模型能力标签和计费方式。

**关键字段**
- 模型名
- 厂商
- 输入价
- 输出价
- 缓存价
- 计费方式
- 平台类型
- 有效成本

**验收标准**
1. 首页能展示至少 10 个模型。
2. 每个模型可点击进入详情页。
3. 用户能切换计费方式筛选。
4. 默认排序可解释。

## FR-2 平台比价

**描述**
- 支持比较官方 API、聚合平台、中转 API、New API 实例。
- 展示平台价格、倍率、充值汇率、支付方式、风险标签。

**关键平台类型**
- `official_api`
- `aggregator`
- `relay`
- `new_api_instance`
- `self_hosted`

**验收标准**
1. 每个平台有类型标签。
2. 每个平台有数据来源。
3. 每个平台有风险提示。
4. 用户能从平台页跳回模型列表。

## FR-3 订阅套餐比价

**描述**
- 收录订阅套餐信息。
- 计算订阅额度折算后的每 1M tokens 成本。
- 展示订阅与按量的破局点。

**关键字段**
- 价格
- 周期
- 总额度
- 额度重置周期
- 模型范围
- 分组升级 / 降级
- 超额规则
- 购买上限

**验收标准**
1. 支持月费 / 年费。
2. 支持额度重置周期。
3. 支持模型范围。
4. 支持超额规则。
5. 能显示“超过多少用量后订阅更划算”。

## FR-4 积分 / 点数 / credits 比较

**描述**
- 记录内部额度、充值汇率、折扣、最低充值、余额有效期、退款规则。
- 把内部额度折算成现金成本。

**关键字段**
- 充值汇率
- 折扣
- 最低充值
- 余额有效期
- 可否退款
- 显示单位
- 是否支持叠加
- 是否限制模型

**验收标准**
1. 能记录 `1 元 = 1 额度`、`1 元 = 1.2 额度` 等比例。
2. 能计算充值系数。
3. 能识别标价与实际成本的差异。
4. 能显示余额有效期。

## FR-5 卡密 / 兑换码 / 网卡路径

**描述**
- 记录是否支持兑换码、使用规则、有效期、售后边界和风险。
- 不把卡密直接当成价格倍率，而是作为购买路径。

**关键字段**
- 是否支持
- 使用规则
- 有效期
- 售后边界
- 获取渠道
- 风险等级

**验收标准**
1. 支持展示是否可用。
2. 支持展示使用规则。
3. 支持展示风险提示。
4. 不与价格公式混淆。

## FR-6 有效成本计算器

**描述**
- 输入模型和月用量，计算按量、订阅、积分和混合策略的真实成本。
- 输出建议和限制条件。

**输入**
- 模型
- 月输入 tokens
- 月输出 tokens
- 缓存命中率
- 并发要求
- 预算
- 是否需要发票

**输出**
- 按量成本
- 订阅成本
- 积分成本
- 推荐路径
- 破局点
- 假设说明

**验收标准**
1. 30 秒内得出结论。
2. 结论包含成本和风险。
3. 支持分享链接。
4. 支持保存假设。

## FR-7 数据可信度与风险提示

**描述**
- 每条价格和平台信息都必须有来源、更新时间和核验状态。

**关键内容**
- 来源链接
- 最近核验时间
- 核验方式
- 上游类型
- 支付方式
- 发票支持
- 退款政策
- 客服入口
- 风险标签

**验收标准**
1. 每条价格可追溯。
2. 每个平台有风险标签。
3. 明确“收录不等于推荐”。
4. 用户可提交纠错。

## FR-8 搜索、筛选与排序

**描述**
- 支持按模型、厂商、能力、平台类型、计费方式、价格、稳定性筛选和排序。

**验收标准**
1. 支持搜索。
2. 支持多条件筛选。
3. 支持有效成本排序。
4. 默认排序不受商业合作影响。
5. 排序口径可解释。

## FR-9 场景推荐

**描述**
- 按典型使用场景输出推荐：
  1. 小额试错
  2. 稳定生产
  3. 高并发
  4. 长上下文
  5. 企业发票
  6. 个人学习

**验收标准**
1. 每个场景有明确的判断规则。
2. 推荐不只看价格，也看稳定性、支付和风险。
3. 能说明为什么不推荐某方案。

## FR-10 营销增长功能

**描述**
- 产品需要内建零预算传播机制。

**功能**
1. 分享卡片
2. 分享链接
3. 嵌入组件
4. 长尾 SEO 页面
5. 破局点页面
6. 场景落地页

**验收标准**
1. 每个核心页面都有可分享资产。
2. URL 可读。
3. 标题符合搜索意图。
4. 用户能复制结论或生成图片。

## FR-11 商业化

**描述**
- 采用清晰、可披露、不影响排序的商业化方式。

**模式**
1. 赞助位
2. 广告位
3. AFF 链接
4. 合作收录
5. 数据服务
6. API 订阅（后续）

**规则**
- 广告位数量固定
- 明确标注“广告 / 赞助 / AFF”
- 不影响自然排序
- 不影响最低价计算
- 不影响风险提示

**验收标准**
1. 商业关系可见。
2. 用户可区分自然收录与广告。
3. 广告主不能要求隐藏风险提示。

## 6. 非目标

5. **不做灰色渠道收录**

## 8. 假设与开放问题

### 8.1 假设
1. 用户更在意准确和可解释，而不是页面华丽。
2. 订阅、积分、卡密在真实平台中确实存在。
3. 零预算营销需要依赖内容、社区和产品自传播。
4. 初期人工核验比大规模自动化更可靠。
5. 技术选型应偏向低成本、静态化和可扩展。

### 8.2 开放问题
1. 是否先聚焦 New API / 中转平台？
2. 是否需要用户提交与审核工作流？
3. 订阅默认折算周期是否为 30 天？
4. 是否做开源数据集以增强传播？
5. 是否引入平台真实调用测试？
